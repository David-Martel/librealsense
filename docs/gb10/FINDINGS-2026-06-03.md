# DGX Spark / GB10 RealSense — Session Findings & TODO (2026-06-03)

Host `spark-3066` · Intel RealSense **D435** · NVIDIA **DGX Spark / GB10** · Ubuntu 24.04.4 · kernel 6.17.0-1021-nvidia.
Full analysis package in [`analysis/`](analysis/); controller-death evidence summaries in [`forensics/`](forensics/).

## TL;DR

1. **The xHCI "controller death" is an NVIDIA GB10 silicon/firmware defect (not librealsense).** Reproduced
   **three times across BOTH backends** (RSUSB *and* native V4L2/uvcvideo). The GB10 `xhci_plat_hcd`
   (ACPI `NVDA8000`) cannot complete a **Stop-Endpoint** command after **any** control-path `-110` timeout,
   and has **no recovery path** → `HC died` → reboot required. **No userspace backend choice or librealsense
   patch can prevent it** — only an NVIDIA BSP/firmware fix.
2. **Shipped safe envelope: SINGLE high-rate stream only (UNCHANGED, deliberately conservative).** In the
   dock-contended / USB-2 era, **dual 848×480@60 killed a controller** (incident #3) and 3-stream was lethal
   (incident #1) — those facts stand. **Preliminary update (2026-06-03, [`HIL-MULTISTREAM-2026-06-03.md`](HIL-MULTISTREAM-2026-06-03.md)):**
   on the *current* full config (RSUSB + **clean USB-3 dedicated bus** + P2/P3/P4/P7 active), dual+align,
   4-cycle start/stop churn, and 4-stream all **survived** short runs with **zero `-110` control timeouts** —
   consistent with "the death requires a `-110`; absent it, the Stop-Endpoint is never armed." This is **not** an
   envelope relaxation: four variables changed at once (bus, mitigations, backend, build), runs were ~5 s, and it
   wasn't reproduced on V4L2. Keep single-stream for anything that must not fail; a multi-minute soak + cycle-to-death
   on both backends is required before the envelope can widen.
3. **librealsense mitigations P2/P3/P4 are implemented, statically validated, and opt-in** — they reduce the
   *trigger* but cannot fix the crash. **P1 (eager uvcvideo detach) and P5 (udev unbind) were DROPPED as
   contraindicated** (the unbind mechanism itself can wedge the GB10 controller).
4. **CUDA OpenCV 4.14 + NVENC stack integrated** into the GB10 build (from `/opt/gb10-cuda/install`).

## The three controller deaths (NVIDIA P6 escalation evidence)

| # | Date/time | Backend | Trigger | Forensics |
|---|-----------|---------|---------|-----------|
| 1 | 2026-06-02 21:59 | RSUSB | 3× 848×480@60 concurrent bulk saturation | `forensics/20260602-2159-…` |
| 2 | 2026-06-03 08:04 | RSUSB | context/pipeline teardown → kernel-uvcvideo reclaim/re-probe → `-110` storm (see correction below) | `forensics/20260603-0804-…-2` |
| 3 | 2026-06-03 09:02 | **V4L2 (kernel uvcvideo)** | **dual** D+C 848×480@60 setup control timeout | `forensics/20260603-0902-…-3-V4L2` |

All end identically: `xhci-hcd NVDA8000:0X: xHCI host not responding to stop endpoint command` →
`Host halt failed, -110` → `HC died`. Incident #3 on the **native V4L2 backend** is the decisive proof the
defect is not RSUSB/librealsense-specific. **File all three with NVIDIA** (DGX Spark BSP/xHCI Stop-Endpoint
hardening + a controller re-init path equivalent to Jetson `tegra_xhci_hcd_reinit()`).

> **Correction (2026-06-03, re-forensicated from cached artifacts — supersedes the earlier death-#2
> "unadvertised profile" framing).** Death #2 was **not** caused by a bad profile and **not** by a degraded
> link: (1) the requested `Color 848×480@60 BGR8` **resolved fine** to the native `YUYV @60`
> (`formats-converter.cpp:234/277`) — the D435 advertises `Color 848x480 RGB8 @ 60/30/15/6 Hz`
> (`rs-enumerate.txt:68`), so a membership/advertised-set guard would never have fired; (2) the link was
> **USB-3.2** (`Usb Type Descriptor: 3.2`, port `2-1-2`) on every enumeration incl. two healthchecks ~40 min
> prior. The real trigger was **churn**: the (now-deprecated) harness destroyed and recreated the whole
> `rs2::context`+pipeline between depth and color (`context.cpp:41 loading defaults` reappears at 08:03:43),
> releasing the device back to **kernel uvcvideo**, which re-probed UVC control endpoints → `-110` storm
> (08:03:48–08:03:59) → lethal Stop-Endpoint → `HC died` (08:04:09). By the time `color open()` ran it hit
> `RS2_USB_STATUS_NO_DEVICE` — **the controller was already dead before the color profile was issued.** The
> safe pattern is *session-stable device ownership* (one context per process, reconfigure via `rs2::config`),
> now enforced advisorily by the **P7 re-acquire guard** (`src/usb-tuning.h` `resolve_reacquire_action`,
> wired in `src/libusb/device-libusb.cpp`). The membership guard below is demoted to a low-priority
> "never issue an unadvertised config" nicety — correct in principle, but not what killed the controller.

## librealsense changes in this branch

### Opt-in GB10 RSUSB multistream mitigations (`RS2_GB10_USB_TUNING`)
Pure decision helpers in [`src/usb-tuning.h`](../../src/usb-tuning.h) (TDD unit-tested,
[`unit-tests/usb-tuning/`](../../unit-tests/usb-tuning/)), gated by the compile define `RS2_GB10_USB_TUNING`
(bridged to a `target_compile_definitions` in `CMakeLists.txt`; the GB10 build profile passes
`-DRS2_GB10_USB_TUNING=1` via `LRS_GB10_USB_TUNING`). **Undefined upstream ⇒ byte-identical to stock** (verified:
both define-on and define-off compile clean).

| ID | Mitigation | Where | Default (GB10 / upstream) | Runtime override |
|----|-----------|-------|---------------------------|------------------|
| P2 | Deeper per-stream URB pool | `src/uvc/uvc-device.cpp` `create_rsuvc_device` | 4 / 2 | `RS2_USB_REQUEST_COUNT` |
| P3 | `usbfs_memory_mb` advisory at open (one-time, read-only) | `src/libusb/device-libusb.cpp` | gated on/silent | — |
| P4 | Watchdog reset rate-limit + inter-stop settle | `src/uvc/uvc-streamer.{cpp,h}`, `uvc-device.cpp::close` | 250ms / 50ms vs 0 | `RS2_USB_STOP_SETTLE_MS` |

P4 (gentler stop) targets the Stop-Endpoint storm both root-cause theories agree is fatal — the most robust of
the set. Spec: [`analysis/85-librealsense-patch-specs.md`](analysis/85-librealsense-patch-specs.md).
**Status: statically validated (compiles, unit-tested, code-reviewed) but NOT HIL-validated** (HIL is gated on a
reboot; and the crash itself is not preventable in userspace — see TL;DR).

### CUDA media-stack integration

  → passes `-DOpenCV_DIR` so the CV examples/wrappers link **CUDA OpenCV 4.14.0** (cv2.cuda) instead of stock

- GPU preview helper + integration notes: [`analysis/90-cuda-integration.md`](analysis/90-cuda-integration.md).
  Env gotcha: cv2.cuda needs `/opt/gb10-cuda/install/{opencv,ffmpeg}/lib` on `LD_LIBRARY_PATH` (else

### librealsense / build (do-now, code)
- [ ] HIL-validate P2/P3/P4 post-reboot: `rs-gb10-hil.sh --render` **single-stream only**; capture
      `create_rsuvc_device: usb_request_count=4` proof. (Harness lives in `~/realsense-gb10-validation/`.)
- [x] **P7 device re-acquire guard (the real death-#2 pre-emptive guard) — DONE.** *Detects* the verified
      death-#2 *churn* — a full release of the device (all handles destroyed) followed by a re-acquire, which is
      what hands the device back to kernel uvcvideo. Pure helpers `is_dangerous_reacquire` (live-instance count:
      dangerous only when live==0 after a prior acquire — so it does NOT false-fire on the depth+color sensors of
      one session) + `resolve_reacquire_action`/`reacquire_advice` in `src/usb-tuning.h` (TDD unit-tested, P7 cases;
      Catch2 + standalone gate green), wired at three call sites in `src/libusb/device-libusb.cpp` (ctor check +
      ctor-end commit + dtor release of a per-device live counter keyed by USB bus-port `unique_id`). Opt-in via
      `RS2_GB10_USB_TUNING` (byte-identical upstream); **advisory `WARN` by default**, hard-`REFUSE` only via
      `RS2_GB10_REFUSE_REACQUIRE=1`. Never auto-detaches uvcvideo (the contraindicated P1/P5). **RSUSB-only** (the
      V4L2 production backend never constructs `usb_device_libusb`). *Honest scope:* it fires at re-acquire, which
      is **after** the prior release already in flight — so on a single churn it detects/steers rather than
      prevents; its prevention value is halting a repeated stop/recreate loop (REFUSE) and the advisory itself.
      **Default-on caveat:** `RS2_GB10_USB_TUNING` is set in the GB10 build profile, so this guard ships ON (WARN)
      in that build. Death-2 log support that it does *not* false-fire on a normal session: the 4
      `create_rsuvc_device` constructions at startup (08:03:20.796–.994) show **no** `set_power(D3)`/release/close
      between them or through the intentional 08:03:43 teardown, and `rs_uvc_device` retains its `usb_device_libusb`
      — so live climbs 0→N and never returns to 0 mid-session. Not yet iron-clad (a never-powered transient probe
      object could destruct without a `D3` log). **HIL-CONFIRMED 2026-06-03 (single-context open on the GREEN
      USB-3 bus, RSUSB build, under the strict `RS2_GB10_REFUSE_REACQUIRE=1`):** `create_rsuvc_device` ran **4×**
      for the one D435, both sensors enumerated fully (Stereo Module 104 profiles + RGB Camera 161 profiles),
      depth streamed 60 frames, controller stayed GREEN, and the guard **never fired** (REFUSE was a silent
      no-op). I.e. the 4 same-`unique_id` constructions are held concurrently (live 0→4, never 0) so the guard
      does NOT false-fire — verified by behavior, not just logs (a false-positive under REFUSE would have thrown
      and dropped the RGB Camera). Still open (not run, deliberately — it re-runs the killer): confirm a forced
      context-recreate *trips* the guard (the trip direction is unit-tested via `is_dangerous_reacquire(0,1)=true`).
      Follow-up: HIL-confirm WARN stays silent on a legitimate single-context session.

  Use `uv run python` / the project uv venv = **3.12.3**. pyrealsense2 + cv2 are cpython-312; numpy pinned 1.26.4.
- USB topology: native rear-panel Type-C + eMarker cable only (never a dock's USB-2.0 hub chain). Map a USB
  bus→xHCI controller via `readlink -f /sys/bus/usb/devices/usbN/..`.
